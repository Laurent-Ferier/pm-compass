TaskList
class

The <ul> every list of tasks the Dashboard and Inbox show is made of, whatever the settings put in it — one day's checklist, several days' unclosed lines, project tasks, or any mix. Holds BaseTasks and owns only where a row goes: the order (by date, undated last, stable) and the drag-to-reorder the rows of one file share. How a row looks is the view's, passed once as a RenderTaskRow. Every row gets the grip's slot, inert where there is no order to persist, so the lists sharing a screen line up.

MoveTargetModalextends Modal
class

Picks a destination for a task, as one collapsible tree: projects at the top level, each opening into its own task tree a level at a time. Picking a project row means that project's root; picking a task row means under that task. Completed tasks are hidden by default (hideCompleted), except where they are the only route to open work below. Serves both callers that send a task somewhere — promoting a checklist line, and moving an existing task — which differ only in whether a brand-new project is on offer (allowNewProject) and which destinations are legal (isDisabled, which greys a row out and shows the refusal reason on hover).

fieldsopts: MoveTargetModalOptions, selectedProject, selectedParent, newProjectTitle, hideCompleted, expanded, renderHost
opened by → BaseTabView (openPromoteModal, openTaskContextMenu), TaskGraphView validates via → isValidMoveTarget (model/shared) calls → moveTask (model/operations/task-move)

BaseNote
abstract class

A note that lists other notes as a - [ ] [[child]] checklist: a project listing its root tasks under ## Tasks, a task listing its subtasks under ## Subtasks. The two differ only in which section holds the list and where the children's notes sit, so each subclass answers those and inherits the rest. Registering a child reads the child's own status for the box rather than trusting the caller's — a stale list would tick a task reopened since. applyChildBoxes pushes the boxes onto the tasks; repairChildBoxes does the reverse, and is what a listing gets until it is known to agree with its tasks.

abstractchildSection · childFolder · childNote(path) methodsaddChild() · removeChild() · applyChildBoxes(body) · repairChildBoxes(body) · syncChildListing(children)
extended by → ProjectFile, ProjectTaskFile writes via → child-links (addChildLink/removeChildLink/setChildLinkBoxes/syncChildLinks) driven by → syncChangedNote, repairListings
ProjectFileextends BaseNote
class

Typed read/update/create of one project root note. Owns its frontmatter (title, color, icon) and its taskIds + ## Tasks list of root-level tasks — a denormalized copy this plugin never reads back (the tree comes from parentId), maintained so obsidian-pm's own board stays correct and kept in step with the tasks by the listing sync. Only root-level tasks are listed here; nested ones belong to their parent task. create() writes that plugin's full schema, including fields nothing here consumes. Analogous to DayMarkdownFile but for a single-record file instead of a multi-task list.

fieldsfilePath methodsreadMetadata() · update(data) · (listing methods from BaseNote) staticcreate(app, opts)

ProjectTaskFileextends BaseNote
class

Typed read of one task note's subtask ids and description, and patch of its status/priority frontmatter — including side effects like auto-stamping a completed date. Also both ends of the listing sync for a task: pushToListing mirrors its title and status onto the checklist line that names it (found via the Project:/Parent: prefix its body opens with), and applyParentBox closes or reopens it to match a box flipped by hand in its parent — asking the file rather than the metadata cache before writing, since the parent's event can outrun this note's own reparse. Analogous to DayMarkdownFile but per-task instead of per-day.
